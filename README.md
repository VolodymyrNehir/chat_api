# Chat API з обліком токенів і вартості

## 1. Що це

REST API для чат-сесій поверх OpenAI: кожна відповідь моделі будується на
релевантній історії сесії під токен-бюджетом, а кожна взаємодія обліковується
в токенах і в доларах.

## 2. Стек

- **Node.js 22+**, **TypeScript**
- **NestJS** — працює на платформі Express (`@nestjs/platform-express`), тобто
  вимога ТЗ щодо Node.js/Express.js виконана
- **PostgreSQL 16** (у Docker) + **TypeORM** (`@nestjs/typeorm`) — точний тип
  `numeric` для грошей, транзакції, foreign keys
- **OpenAI Responses API** (`store: false`, стан сесії лишається в нашій БД)
- **`gpt-tokenizer`** (кодування `o200k_base`) для підрахунку токенів у вікні
  контексту
- **`class-validator`** для валідації запитів, **Joi** (через `@nestjs/config`)
  для валідації змінних оточення при старті
- **Swagger UI** на `/docs`, мінімальний chat UI без збірки на `/`
- **Docker Compose** (`api` + `db`) і **Makefile** як єдина точка входу

## 3. Запуск

```bash
cp .env.example .env
```

Відкрити `.env` і вписати два значення:

- `OPENAI_API_KEY` — робочий ключ OpenAI
- `POSTGRES_PASSWORD` — будь-який пароль на свій розсуд

> **Пастка з паролем Postgres.** Образ `postgres` застосовує
> `POSTGRES_PASSWORD` лише під час **першої** ініціалізації (`initdb`) на
> порожньому томі. Якщо `.env` відредаговано вже після першого `make up`,
> новий пароль до наявної ролі не дійде, і `api` впаде з `28P01` (password
> authentication failed), а не помітно, чому. Чистий вихід — не редагувати
> пароль заднім числом, а `make reset` (видаляє том) і `make up` заново.

Далі:

```bash
make up
```

Це збирає образ, піднімає `db` і `api` та прогонить міграції — одна команда,
без локального Node чи Postgres.

Застосунок слухає порт `3000` **всередині контейнера** завжди (значення
`PORT` з `.env`). Якщо на хості порт `3000` зайнятий іншим процесом, задайте
інший порт хоста змінною `HOST_PORT`, не чіпаючи `PORT`:

```bash
HOST_PORT=3100 make up
```

Після старту:

- API: `http://localhost:3000` (або `http://localhost:$HOST_PORT`, якщо
  задавали `HOST_PORT`)
- Swagger: `http://localhost:3000/docs`
- Мінімальний chat UI: `http://localhost:3000/`
- `GET /health` — простий liveness-ендпоінт (`{"status":"ok"}`, без звернень
  до БД чи OpenAI). Саме його опитує `healthcheck` сервісу `api` в
  `docker-compose.yml`, тому `docker compose ps` показує не просто "контейнер
  піднявся", а "застосунок відповідає на HTTP".

Інші корисні цілі: `make down` (зупинити, том лишається), `make reset`
(зупинити й видалити том — чиста база), `make logs`. Повний список — `make`
без аргументів.

`make up`, `make down`, `make reset`, `make logs` і `make ps` не потребують
ані локального Node.js, ані локального Postgres — усе виконується всередині
контейнерів. Винятки: **`make test`** і **`make migration`** запускаються на
хості (`npm test` / `npm run migration:generate` напряму) і потребують
встановленого локального Node.js 22+ та `npm ci` — Docker для них не
задіяний.

## 4. Ендпоінти

Усі відповіді — JSON, camelCase. Грошові поля — рядки з 10 знаками після коми
(точна арифметика, без втрати точності при серіалізації).

### `POST /sessions`

| Request | Response `201 Created` |
|---|---|
| `title`, `systemPrompt`, `model` — усі необов'язкові | `id`, `title`, `model`, `systemPrompt`, `createdAt`, `messageCount`, `totalCostUsd` |

```jsonc
// request
{
  "title": "Демо сесія",
  "systemPrompt": "You are a helpful assistant.",
  "model": "gpt-5-nano"
}

// 201 Created
{
  "id": "3f1c...",
  "title": "Демо сесія",
  "model": "gpt-5-nano",
  "systemPrompt": "You are a helpful assistant.",
  "createdAt": "2026-08-31T12:00:00.000Z",
  "messageCount": 0,
  "totalCostUsd": "0.0000000000"
}
```

`model` валідується проти таблиці тарифів (розділ 6 нижче). Непідтримувана
модель -> `400 UNSUPPORTED_MODEL` зі списком підтримуваних.

### `POST /sessions/{id}/messages`

| Request | Response `200 OK` |
|---|---|
| `content` — непорожній рядок, до `MAX_MESSAGE_CHARS`; `model` — необов'язковий | `message`, `usage`, `cost`, `context`, `session` |

```jsonc
// request
{ "content": "Привіт! Що ти вмієш?" }
// або з явною моделлю на це одне повідомлення
{ "content": "Привіт! Що ти вмієш?", "model": "gpt-5-mini" }

// 200 OK
{
  "sessionId": "3f1c...",
  "message": {
    "id": "9ab2...",
    "role": "assistant",
    "content": "...",
    "createdAt": "2026-08-31T12:00:05.120Z"
  },
  "usage": {
    "model": "gpt-5-nano",
    "inputTokens": 412,
    "cachedInputTokens": 0,
    "outputTokens": 178,
    "reasoningTokens": 64
  },
  "cost": {
    "inputCostUsd": "0.0000206000",
    "outputCostUsd": "0.0000712000",
    "totalCostUsd": "0.0000918000",
    "currency": "USD"
  },
  "context": {
    "messagesSent": 11,
    "messagesOmitted": 4,
    "estimatedInputTokens": 405,
    "tokenBudget": 8000
  },
  "session": {
    "totalCostUsd": "0.0004410000",
    "messageCount": 14
  }
}
```

`model` — необов'язкове поле, перевизначає дефолт сесії лише для цього
одного повідомлення; `sessions.model` при цьому **не змінюється**. Валідується
так само, як `model` при створенні сесії: непідтримувана модель -> `400
UNSUPPORTED_MODEL` зі списком підтримуваних, порожній рядок або самі пробіли
відхиляються валідацією DTO. `usage.model` у відповіді завжди показує
фактично використану модель, і саме за її тарифом порахований `cost`.

Блок `context` — не декорація: це видимий доказ того, що в модель пішла саме
релевантна історія (див. розділ 8).

`context.messagesSent` — довжина повного масиву, надісланого моделі: system
prompt + head-повідомлення + маркер пропуску (якщо він був вставлений) +
tail-повідомлення + нове повідомлення користувача. Це **не** те саме, що
кількість повідомлень історії, які реально потрапили у вікно (head + tail) —
той підрахунок зберігається окремо, в колонці `history_messages_sent` таблиці
`interactions`, і не вертається клієнту напряму.

### `POST /sessions/{id}/reset`

Без тіла запиту. Нічого не створюється, тож статус — `200 OK`, у тій самій
формі, що й `GET /sessions/{id}`, щоб клієнт міг просто замінити свій стан
відповіддю:

```jsonc
// 200 OK
{
  "id": "3f1c...",
  "title": "Демо сесія",
  "model": "gpt-5-nano",
  "generation": 2,
  "systemPrompt": "You are a helpful assistant.",
  "createdAt": "...",
  "updatedAt": "...",
  "messages": [],
  "totals": {
    "messageCount": 0, "interactionCount": 0,
    "inputTokens": 0, "cachedInputTokens": 0,
    "outputTokens": 0, "reasoningTokens": 0,
    "totalCostUsd": "0.0000000000"
  },
  "lifetime": {
    "messageCount": 14, "interactionCount": 7,
    "inputTokens": 2840, "cachedInputTokens": 0,
    "outputTokens": 1204, "reasoningTokens": 380,
    "totalCostUsd": "0.0004410000"
  }
}
```

Сесію не знайдено -> `404 SESSION_NOT_FOUND`.

**Reset архівує, а не видаляє.** На сесії з'являється лічильник `generation`,
на повідомленнях і взаємодіях — власна колонка `generation`. Reset інкрементує
лічильник сесії, і все, що записано під попереднім поколінням, автоматично
перестає бути активним, лишаючись у базі без змін. Причина не в обережності, а
в предметі проєкту: `interactions` — це журнал фактичних оплачених викликів до
OpenAI, і видаляти записи про реально витрачені гроші через натискання кнопки
в інтерфейсі означало б зробити цей журнал недостовірним — сума за сесію
більше не відповідала б тому, що виставить OpenAI. Блок `lifetime` — те, що
робить збережену історію видимою через API, а не просто теоретичним
твердженням.

Reset порожнього поточного покоління (жодного повідомлення не надіслано після
попереднього reset або створення сесії) — no-op: лічильник не зростає, у
відповіді повертається те саме `generation`. Інакше повторні натискання кнопки
в UI роздували б лічильник, і `generation` показував би кількість натискань,
а не кількість реальних скидань.

  ],
  "totals": {
    "messageCount": 14,
    "interactionCount": 7,

`generation` — номер поточного покоління контексту; кількість виконаних

поколінням — сума за всю сесію, включно з тим, що вже заархівовано.

### Формат помилки

```jsonc
{
  "statusCode": 422,
  "error": "Unprocessable Entity",
  "code": "CONTEXT_BUDGET_EXCEEDED",
  "message": "Message does not fit the context budget (needs 9210 tokens, budget 8000)",
  "path": "/sessions/3f1c.../messages",
  "timestamp": "2026-08-31T12:00:05.120Z"
}
```

| Ситуація | Статус | `code` |
|---|---|---|
| Порожній / завеликий `content`, некоректний UUID | 400 | `VALIDATION_FAILED` |
| Непідтримувана модель | 400 | `UNSUPPORTED_MODEL` |
| Сесію не знайдено | 404 | `SESSION_NOT_FOUND` |
| Конкурентна вставка в ту саму сесію | 409 | `SEQUENCE_CONFLICT` |
| Повідомлення не влазить у токен-бюджет | 422 | `CONTEXT_BUDGET_EXCEEDED` |
| OpenAI повернув 429 | 429 | `UPSTREAM_RATE_LIMITED` (з `Retry-After`, якщо є) |
| OpenAI 5xx або мережева помилка | 502 | `UPSTREAM_ERROR` |
| Таймаут виклику OpenAI | 504 | `UPSTREAM_TIMEOUT` |

Ключ OpenAI, сирі відповіді SDK та стек-трейси клієнту не повертаються —
глобальний фільтр логує повне повідомлення провайдера на сервері, а клієнту
віддає лише нормалізований код і фіксований текст.

## 5. Перевірка

Найпростіше — файл `requests.http` у корені (працює прямо у WebStorm/IDEA, а
також у розширенні REST Client для VS Code): відкрити файл і виконати запити
по порядку.

Той самий сценарій через `curl`:

```bash
SID=$(curl -s -X POST localhost:3000/sessions \
  -H 'content-type: application/json' \
  -d '{"title":"smoke"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

curl -s -X POST localhost:3000/sessions/$SID/messages \
  -H 'content-type: application/json' \
  -d '{"content":"Say hello in exactly three words."}' | python3 -m json.tool

curl -s -X POST localhost:3000/sessions/$SID/messages \
  -H 'content-type: application/json' \
  -d '{"content":"How many words were in your previous answer?"}' | python3 -m json.tool

curl -s localhost:3000/sessions/$SID | python3 -m json.tool
```

Друге повідомлення явно спирається на перше («скільки слів було в попередній
відповіді?») — модель може відповісти правильно, лише якщо історія сесії
справді дійшла до неї в контексті. Це і є доказ роботи історії, а не просто
факт, що ендпоінт відповідає 200.

Заміните `localhost:3000` на `localhost:$HOST_PORT`, якщо піднімали з
власним `HOST_PORT`.

## 6. Модель і тарифи

Ставки — статичний знімок офіційної сторінки тарифів OpenAI
(https://openai.com/api/pricing/) від **2026-08-31**, у `pricing_source =
"openai-public-2026-08-31"`. Ставки не підтягуються з інтернету в рантаймі —
таблиця в `src/config/pricing.config.ts` оновлюється вручну, свідомо.

USD за 1M токенів:

| Модель | Input | Cached input | Output | Reasoning |
|---|---:|---:|---:|:---:|
| `gpt-5` | 1.25 | 0.125 | 10.00 | так |
| `gpt-5-mini` | 0.25 | 0.025 | 2.00 | так |
| `gpt-5-nano` (за замовчуванням) | 0.05 | 0.005 | 0.40 | так |
| `gpt-4.1-mini` | 0.40 | 0.10 | 1.60 | ні |
| `gpt-4o-mini` | 0.15 | 0.075 | 0.60 | ні |

### Формула

```
billableInput = inputTokens − cachedInputTokens

inputCost  = billableInput      / 1e6 × inputPerMTok
           + cachedInputTokens  / 1e6 × cachedInputPerMTok

outputCost = outputTokens       / 1e6 × outputPerMTok

totalCost  = inputCost + outputCost
```

Два місця, де легко помилитись (обидва закриті тестами в
`test/pricing.service.spec.ts`):

- **Кешовані токени.** `usage.input_tokens_details.cached_tokens` уже входить
  у загальний `input_tokens`, тому перед множенням на повну ставку його треба
  **відняти** від `inputTokens`, а не рахувати окремо поверх. Кешований токен
  тарифікується за нижчою ставкою (для `gpt-5-nano` — у 10 разів дешевше).
  Без віднімання вартість систематично завищується.
- **Reasoning-токени.** У сімействі GPT-5 вони **вже включені** в
  `output_tokens`, який повертає OpenAI. Значення зберігається окремим полем
  для прозорості (звідки в звіті видно, скільки з output пішло на
  міркування), але **не додається повторно** до вартості.

## 7. Категорії usage, які не враховуються

API не використовує відповідні можливості OpenAI, тому ці категорії в наших
відповідях не з'являються і в розрахунок вартості не входять:

- **audio-токени** (голосовий ввід/вивід)
- **токени вбудованих інструментів** (web search, file search, code
  interpreter)
- **генерація зображень**

Якщо якась із цих категорій колись з'явиться у відповіді OpenAI, вона не буде
врахована в нашій вартості — це виявиться як розбіжність між нашою сумою і
рахунком в OpenAI, а не мовчки проковтнеться.

## 8. Як будується контекст

**Стратегія: head + tail під токен-бюджетом** — спрощений middle-out.

Обґрунтування спирається на статтю «Lost in the Middle: How Language Models
Use Long Contexts» (Liu et al., 2023, https://arxiv.org/abs/2307.03172): вона
показує, що точність моделі найвища, коли релевантна інформація стоїть на
початку або в кінці контексту, і просідає, коли вона в середині. Той самий
принцип лежить в основі трансформу `middle-out` в OpenRouter.

Коротко про алгоритм (`src/chat/history.builder.ts`, чиста функція без БД і
мережі):

1. Системний промпт і нове повідомлення користувача входять у контекст
   завжди; якщо їхня сума вже перевищує бюджет — `422
   CONTEXT_BUDGET_EXCEEDED`.
2. **Head** — перші повідомлення історії, доки не вичерпають свою частку
   бюджету (обмежена і кількістю, і часткою, щоб одне довге перше
   повідомлення не з'їло все вікно).
3. **Tail** — від найновішого повідомлення назад, доки влазить у залишок
   бюджету; на першому повідомленні, що не влазить, набір зупиняється (без
   пропусків, щоб не утворювати дірок у діалозі).
4. Якщо між head і tail лишився пропуск, у масив, що йде в OpenAI, вставляється
   службове `system`-повідомлення про пропуск — воно ніколи не зберігається
   в БД, тільки в самому запиті до моделі.

Ручки в `.env`, що керують вікном:

| Змінна | Що робить |
|---|---|
| `HISTORY_TOKEN_BUDGET` | загальний бюджет токенів на контекст (system + head + tail + нове повідомлення) |
| `HISTORY_PINNED_HEAD_MESSAGES` | скільки перших повідомлень історії розглядати під head |
| `HISTORY_HEAD_MAX_SHARE` | яку частку залишку бюджету (0–1) дозволено віддати під head |
| `HISTORY_GAP_MARKER` | чи вставляти службове повідомлення про пропуск, коли між head і tail є дірка |

## 9. Тести

```bash
make test
```

Jest, 59 тестів. Свідомо покрита **чиста логіка** — місця, де
помилка пройшла б непоміченою в демо, але видно на кожному реальному
рахунку:

- **`pricing.service.spec.ts`** — розрахунок вартості: по одному кейсу з
  точним очікуваним значенням на кожну з п'яти моделей, кешовані токени за
  зниженою ставкою й без подвійної оплати, reasoning-токени не додаються
  поверх output, нульовий usage дає нульову вартість, невідома модель кидає
  `UnsupportedModelError`, знімок тарифів прив'язаний до
  `openai-public-2026-08-31`.
- **`history.builder.spec.ts`** — збірка вікна контексту: коротка історія
  входить повністю, довга ріжеться на head+tail з правильними лічильниками
  (включно з `historyMessagesSent`, окремим від повного `messagesSent`),
  завелике нове повідомлення кидає помилку бюджету, head понад свою частку
  відкидається на користь свіжості, маркер пропуску з'являється тільки коли
  дірка справді є, результат завжди хронологічний.
- **`model-resolver.spec.ts`** — резолюція моделі повідомлення (Крок 4): без
  `requested` повертається дефолт сесії, явний `requested` перемагає дефолт,
  непідтримуваний `requested` і непідтримуваний дефолт сесії обидва кидають
  `UnsupportedModelError` з непорожнім списком підтримуваних, прототипні
  імена (`constructor`, `toString`) не проходять як модель.
- **`http-exception.filter.spec.ts`** — кожна доменна помилка мапиться на
  задокументований статус і код, невідома помилка дає 500 з фіксованим
  повідомленням і без стек-трейсу в тілі, деталі `QueryFailedError` (SQL,
  `driverError`) ніколи не потрапляють у відповідь клієнту.

Усі чотири — чисті модулі або тести з фейковим `ArgumentsHost`, без доступу до
БД чи мережі, тому швидкі й детерміновані. Плюс `env.validation.spec.ts`
(валідація конфігурації, включно з `DEFAULT_MODEL` проти таблиці тарифів) і
`openai.provider.spec.ts` (нормалізація відповіді OpenAI, класифікація
помилок провайдера на потрібні доменні типи, відмова від порожньої або
незавершеної відповіді).

Наскрізного (e2e) покриття чат-флоу, розрахунку вартості чи побудови
контексту немає — це свідомий вибір, узгоджений з обмеженим таймбоксом; без
реального ключа OpenAI такі тести однаково не змогли б пройти повний цикл.

Reset сесії тестами не покритий і перевіряється **вручну**. Він живе на рівні
репозиторію — транзакція з `SELECT ... FOR UPDATE` над рядком сесії — і
потребує реальної бази, а інтеграційних тестів у проєкті свідомо немає (вище
в цьому розділі). Сценарій перевірки — послідовність запитів у
`requests.http` (розділ 5): створити сесію, надіслати повідомлення, `reset`,
переконатися, що `id` не змінився, `generation` зросло, активні `messages`
і `totals` порожні, а `lifetime` зберіг суму до reset.

## 10. Відомі обмеження

1. Два одночасні повідомлення в одну сесію бачать однакову історію (обидва
   читають стан до запису одне одного). Унікальний індекс `(session_id,
   seq)` не дає зіпсувати нумерацію: конфлікт відкочує транзакцію й поверне
   `409 SEQUENCE_CONFLICT`. Продакшн-відповідь — `pg_advisory_xact_lock` на
   сесію, який серіалізує обміни в межах однієї сесії; у цьому таймбоксі не
   реалізовано.
2. Reset, що стається, поки повідомлення в тій самій сесії ще в польоті:
   `sendMessage` читає `generation` на початку обробки, до виклику моделі, і
   штампує запис саме цим значенням. Якщо reset завершиться раніше, ніж
   прийде відповідь моделі, обмін запишеться у вже заархівоване покоління, а
   не в те, що стало активним після reset. Свідомий вибір: питання, поставлене
   до reset, і відповідь на нього лишаються разом в одному поколінні, а свіжий
   контекст після reset справді порожній — альтернатива (перечитати
   `generation` усередині транзакції запису) означала б, що повідомлення,
   надіслане до reset, з'явиться в контексті вже після нього, тобто reset не
   був би чистим.
3. Немає автентифікації, авторизації та rate limiting.
4. Немає streaming — відповідь віддається цілком.
5. Немає пагінації в `GET /sessions/{id}`: дуже довга сесія поверне велике
   тіло.
6. Таблиця тарифів ведеться вручну; знімок ставок від 2026-08-31.
7. Вартість рахується з usage, який повідомляє OpenAI; звірки з біллінговим
   API немає.
8. Наш підрахунок токенів — оцінка для побудови вікна; тарифікація завжди йде
   за цифрами OpenAI. Розбіжність видно в `estimatedInputTokens` поруч із
   фактичним `inputTokens`.
9. Категорії usage з розділу 7 не обробляються.
10. Немає ідемпотентності: повторний `POST` створює новий обмін.
11. Немає списку сесій (`GET /sessions`) — chat UI тримає поточний
    `sessionId` у `localStorage`.
12. Секрети лежать у `.env` відкритим текстом. Для локального запуску це
    нормально, у продакшні їхнє місце в секрет-менеджері, а не у файлі поруч
    з кодом.
13. Міграції проганяються при кожному старті контейнера. Ідемпотентно й
    зручно для демо, але в продакшні міграції — окремий крок деплою, а не
    частина запуску.

## 11. Що зробив би далі

- **Advisory lock на сесію** (`pg_advisory_xact_lock`) — прибирає гонку з
  пункту 1 вище: серіалізує обміни в межах однієї сесії замість покладатися
  на конфлікт унікального індексу й повторний запит клієнта.
- **Сумаризація витісненого контексту** — замість того, щоб просто викидати
  середину діалогу, стискати її одним додатковим викликом моделі в компактний
  підсумок і тримати його поруч із head. Дорожче й складніше в обліку (це
  окремий виклик зі своїм usage), тому свідомо не робилося в цьому таймбоксі.
- **Звірка з біллінговим API OpenAI** — періодично звіряти суму
  `total_cost_usd` за наш облік із фактичним рахунком OpenAI Usage API, щоб
  розбіжність (пункт 7 вище) не була лише теоретичним ризиком, а мала
  автоматичну перевірку.

## 12. Граф знань кодової бази (graphify)

Допоміжний інструмент розробки, **не частина продукту**. [graphify](https://github.com/safishamsi/graphify)
будує з кодової бази навігований граф знань: сутності й зв'язки між ними,
з поділом на спільноти й чесним аудитом походження кожного ребра
(`EXTRACTED` / `INFERRED` / `AMBIGUOUS`).

Вивід лежить у `graphify-out/` і **не комітиться** — це похідний артефакт,
який відтворюється з коду за одну команду:

```bash
uv tool install graphifyy   # або: pip install graphifyy
graphify .                  # -> graphify-out/graph.html, GRAPH_REPORT.md, graph.json
```

Для цього проєкту граф вийшов на **400 вузлів, 590 ребер, 18 спільнот**.
Переважна більшість вузлів (358) видобута з AST — детерміновано й без
жодного виклику моделі; решта 49 — семантичні, з README, `docker-compose.yml`
і сторінки UI.

### Що він показав

Найзв'язніші **сутності коду** — `Message` (19 ребер), `Session` (17) і
`Interaction` (16). Це незалежне підтвердження рішення з розділу 4: облік
вартості винесено в окрему таблицю `interactions`, а не в колонки на
повідомленні, бо вартість належить **виклику API**, а не повідомленню. Граф
будувався з коду, нічого не знаючи про це міркування, і все одно поставив усі
три сутності в центр домену.

Решта верхівки рейтингу — `compilerOptions` і `scripts`, тобто вузли з
конфігів. Це очікувано для невеликої кодової бази: `tsconfig.json` і
`package.json` мають багато полів і структурно домінують над доменним кодом.

### Обмеження

Діагностика графа повідомляє **67 ребер із висячим кінцем** — вони вказують
на символи, яких у графі немає, здебільшого імпорти з `node_modules`, що не
входять у корпус. Тобто покриття не стовідсоткове, і граф варто читати як
карту власного коду, а не всієї системи разом із залежностями. Ще 78 ребер
«схлопнуто»: в неорієнтованому графі пара вузлів тримає одне ребро, тому
шістнадцять посилань `Interaction` на `@Column` з різних рядків стають одним.
Це очікувана поведінка, а не втрата даних.
